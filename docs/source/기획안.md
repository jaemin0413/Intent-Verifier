# 제품 기획안

2026-09-24 합의 기준. 현재 제품 방향의 기본 문서다. [초기 기획](../history/초기기획안-2026-09-17.md)은 원본 이력으로 보존한다. 제품 이름은 미정이다.

## 목적과 대상
학생 팀의 Spring Boot Java 프로젝트에서 **팀원 모두가 Figma를 같은 해석으로 보게 하고**, 그 기획 의도와 실제 Backend 동작의 차이를 찾는다. 홈서버에 띄워 팀이 함께 쓴다. 현재 구현을 정답으로 삼지 않는다. 사용자가 Prompt, 테스트 코드, 테스트 데이터 또는 Fixture를 작성하지 않아도 되는 간편한 도구를 만든다.

## 기본 사용 흐름
1. 관리자가 프로젝트 설정에서 AI, Figma, Notion(API 명세서 링크, 기능명세서 링크 여러 개)과 Backend를 한 번 연결한다. 이 설정은 서버에 저장되어 모든 팀원에게 적용되고 팀원은 설정 없이 기능만 쓴다. Backend 폴더는 개발 후 검사할 때 연결해도 된다. 기능명세서는 프로젝트에 연결하면(선택) 누가 화면을 골라도 함께 읽는다. 도구는 본문과 하위 페이지 한 단계를 읽어 화면과 같은 자격의 원문으로 삼고, 화면과 문서가 어긋나면 질문으로 올리며, 문서가 바뀌면 알리되 자동으로 재해석하지 않는다. Figma 파일은 복사본에서 원본으로 바꿀 수 있고 기존 기록은 유지한다.
2. 선택하거나 보관한 Figma 화면을 분석한다. 이미지뿐 아니라 노드·문구·구조·화면 관계와 제공된 흐름을 읽고 분석 범위와 미확인 범위를 표시한다.
3. 권한·소유권·중복·삭제·정렬·상태 전이처럼 업무 결과를 바꾸는 중요한 불확실성만 질문한다. 팀 정책을 재사용하되 충돌을 표시한다.
4. 요구사항·API 명세·Given/When/Then·미검증 조건을 한 화면에서 검토하고 한 번 승인한다. Backend가 없어도 기획에서 API를 제안하며 기존 API 연결은 선택 사항이다. 비핵심 HTTP 코드 등은 AI가 기본값과 이유를 기록하고 필요할 때 수정할 수 있게 한다.
5. 승인 직후 Notion에 명세를 작성한다. 이미 있는 코드를 검사하므로 상태는 ‘완료’로 적고, 화면·기능명세서에 필요한데 코드에 없는 API는 사용자에게 물어 고른 것만 세부 내용 없이 ‘시작 전’ 행으로 추가한다. 테스트 통과를 문서 작성 조건으로 삼지 않는다.
6. 팀이 Backend를 개발한다. 도구는 Production Code를 작성하거나 수정하지 않는다.
7. 검사 버튼을 누르면 연결된 AI가 승인 기준을 바탕으로 대상 Entity, Repository, 인증, 빌드·테스트 구성을 읽고 Java 테스트와 Given 생성·저장 코드를 테스트 영역에 작성한다. 기존 Fixture가 없어도 생성한다.
8. 대상 프로젝트의 원래 빌드 도구로 실행한다. 기획/실제 차이, 준비 실패, 미검증 조건, 생성 파일과 실행 근거를 보여준다. 결과를 명세 버전에 연결하고 수정 후 재검사한다.

## AI와 사용자의 역할
- 사용자: 중요한 기획 의도를 결정하고 통합 승인한다. 개발과 발견된 구현 오류 수정은 팀이 담당한다.
- 분석 AI: Figma 사실(CONFIRMED), 해석(INFERRED), 미확인(UNKNOWN)을 구분하고 Scan·Node·문구 근거를 보존한다. Given의 역할·관계·상태·비교 데이터는 기획에서 도출한다.
- 연결된 AI: 실제 프로젝트에서 Given을 만드는 코드와 인증·DB 관찰 연결을 작성하고 컴파일·준비 오류를 의미 보존 범위에서 고친다. Backend는 실행 방법의 자료다.
- 도구: 승인·버전·범위·스냅샷·판정·근거를 관리한다. AI가 기대값을 완화하거나 실행 없이 PASS를 선언하지 못하게 한다.

## 팀 공통 해석
- 같은 프로젝트에서 내용이 같은 화면은 누가 골라도 기존 해석을 연다. 새 해석은 명시적으로 요청할 때만 만들고 승인된 기준을 해제하기 전에 확인한다.
- 승인된 명세가 팀 기준이다. 승인자·버전·사용한 AI와 모델을 표시하고 승인 전 내용은 후보로 구분한다. 이름은 표시용이며 신원을 증명하지 않는다.
- 팀원마다 다른 AI를 써도 된다. 누가 어떤 AI로 해석해도 승인된 해석은 팀이 공유하며, 사용한 AI와 모델을 기록한다. 제공자 약관상 팀 서버에서 개인 구독으로 연결할 수 있는 것은 ChatGPT(Codex)뿐이고, 연결하지 않은 팀원은 관리자가 정한 기본 AI를 쓴다.
- 같은 질문에 기능마다 다른 답은 충돌로 표시하고, 자동으로 하나를 고르지 않는다.

## 검증 원칙
- 핵심 기획과 명시적인 API 약속은 엄격히 검사한다. AI가 선택한 비핵심 HTTP 코드의 동등한 차이는 참고 차이로 기록하고 그 차이만으로 업무 기능을 FAIL 처리하지 않는다. 성공/거절의 의미 변화는 동등하지 않다. 판정 정책도 실행 전에 고정한다.
- Given은 삽입 성공뿐 아니라 필요한 계정·권한·관계·상태·비교 데이터가 실제 DB에 존재함을 요청 전에 확인한다. 준비·인증·필수 관찰 문제는 BLOCKED다.
- 검증 대상 업무 계층을 실제 실행한다. Service/Repository를 Mock하여 원하는 결과를 만들지 않는다. 외부 서비스 대체와 검증 경계를 표시한다.
- PASS는 정상 사전조건·실제 요청·필수 관찰·기대 결과가 모두 충족된 실행 근거로만 준다. 정상 준비 후 실제 업무 불일치는 FAIL, 지원하지 않거나 기준/시나리오가 없는 조건은 UNVERIFIED다.
- 모든 요구 조건을 Coverage에 남긴다. 생성된 시나리오만 분모로 삼지 않으며 Frontend와 Backend 범위를 구분한다. 가능한 규칙은 허용/거절 또는 대조 데이터를 함께 검사한다.
- Requirement/API Contract/Scenario 버전을 추적한다. 변경은 영향 검토와 재승인을 거치고 과거 PASS를 현재로 재사용하지 않는다. 실행 직전 승인 기준을 디스크에 동결하고 Backend 상태, 생성 코드, 준비/인증, 요청/응답, DB 전후 상태, 로그를 기록한다.
- 승인 전 컨트롤러·DTO로 API 후보를 제시할 수 있다. 업무 기대값은 원문·사용자 답변에서 정한다. Notion은 승인 명세 출력이며 편집 내용을 자동으로 정답으로 역수입하지 않는다.
- Figma 재스캔·보관함은 완료된 리비전만 공개하고 중단·재시도·분석 범위·원문 연결을 보존한다. Notion은 프로젝트별 위치, 중복 방지, 명세 버전과 변경 이력을 유지한다.

## MVP 범위와 완료 기준
먼저 실제 연결된 한 Spring Boot Java 환경을 지원한다. Figma 선택/보관/재분석, 중요한 질문, 통합 승인, Notion 명세, Java 통합 테스트 생성, 인증·Given 저장, CRUD·소유권·중복·단순 상태/정렬·API 계약 검증과 결과/누락/근거 확인이 MVP다. 전체 Spring 생태계, Frontend QA, 동시성·분산 트랜잭션·복잡한 비동기·외부 사업자 실연동의 자동 검증은 후속 범위다.

완료는 문서나 단위 테스트 개수로 선언하지 않는다. Figma 근거에서 승인까지 추적되고 연결된 프로젝트의 기존 Fixture 없이 연결된 AI가 Java Given/테스트를 생성해 실제 빌드로 실행해야 한다. 올바른 동작 PASS, 기획 불일치 FAIL, 준비 실패 BLOCKED, 누락/미지원 UNVERIFIED를 구분하고 Production Code가 불변이어야 한다. 실제 Notion 연동과 브라우저 흐름의 확인 범위도 별도 기록하며 미확인을 완료로 표시하지 않는다.

## 도구 본체 기술 선택
**현재 Node 본체를 유지한다.** 테스트 대상이 Java라는 이유만으로 서버 전체를 Spring Boot로 옮길 필요는 없다. Given 문제는 테스트 환경·연관 데이터·인증 연결의 문제이며 서버 언어 변경만으로 해결되지 않는다. Figma·Notion·AI 연결·버전 관리의 재작성 비용보다 대상 프로젝트 안에 Java 테스트를 생성하고 원래 빌드로 실행하는 변경의 효과가 크다. 본체 이전은 실사용 성과와 별도 유지보수 필요가 확인될 때 재평가한다.
