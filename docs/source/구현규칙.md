# 구현 규칙

제품 기준은 [기획안](기획안.md)이다. [초기 규칙](../history/초기구현규칙-2026-09-17.md)은 이력이며 충돌하면 현재 문서를 따른다.

1. 대상 Production Code/설정을 수정하지 않는다. 대상 src/test/java, src/test/resources에 도구 소유 파일을 생성할 수 있다. 기존 사용자 파일을 덮어쓰지 않고 원래 빌드로 생성 테스트를 선택 실행한다.
2. Given 의미는 Figma와 승인된 기획에서 정한다. 저장 방법은 승인 후 Entity/Repository/인증/테스트를 읽고 AI가 Java로 작성한다. 기존 Fixture를 필수로 요구하지 않는다.
3. 승인 전 컨트롤러·DTO는 API 후보와 물리적 입력 연결에만 쓴다. Expected·Actor·관계·사전조건·Action·Observation을 Backend에 맞춰 바꾸지 않는다.
4. 기술 기본값에는 출처·이유·엄격/참고 정책을 기록한다. 명시 약속은 엄격히 검사한다. 비핵심 코드의 동등한 차이는 참고 차이지만 성공/거절/서버 오류를 동등하게 취급하지 않는다. 기존 승인 명세를 조용히 재해석하지 않는다.
5. Harness는 도구 소유다. 실행 순서·요청·응답/DB 관찰·Assertion·판정은 고정한다. AI는 프로젝트 구성·Given·인증·사전조건 관찰을 작성한다. 자동 수정은 컴파일/준비 연결에 한정한다.
6. 실행 전 freezeSnapshot과 디스크 기록을 완료한다. Backend Production/빌드 해시, 생성 코드, 입력, Codex 호출 정보, 로그, JUnit 결과, 응답과 DB 전후 상태를 보존한다. 비밀값·토큰을 로그에 노출하지 않는다.
7. 준비/인증/필수 관찰 실패는 BLOCKED, 지원/기준/시나리오 누락은 UNVERIFIED, 정상 준비 후 업무 불일치는 FAIL이다. 실행 완료와 실제 근거가 없으면 PASS가 될 수 없다.
8. 누락 조건을 Coverage에 남기고 대조 검증을 유지한다. 실제 저장·관계·상태를 요청 전에 확인하며 DB 관찰은 flush/clear 후 수행한다. 테스트 DB·외부 의존성 경계를 기록한다.
9. 승인 후 Notion을 작성한다. 전송 실패와 테스트 결과는 별개다. 명세와 검증 상태를 분리하고 프로젝트·버전·중복 방지·이력을 유지한다.
10. Requirement/API/Scenario 변경은 버전·영향 검토·통합 재승인을 거친다. 과거 PASS는 현재로 쓰지 않는다. Figma 완료 리비전·분석 범위·근거를 보존한다.
11. 사용자는 중요한 의도 질문과 한 번의 승인만 수행한다. Prompt/Java/SQL/Fixture/테스트 토큰의 수작업을 요구하지 않는다.
12. npm test와 엔진 경로 변경 시 npm run prove를 실행한다. 새 경로는 npm run prove:native로 실제 연결 증거를 남긴다. 외부 연동 실증과 테스트 대체를 구분한다.
