# 개발 검증 도구 — Codex 분석과 검증 흐름

Figma에서 가져온 기획의 모호한 부분을 확인하고, 승인한 기준으로 Spring Boot 동작을 검증합니다. 제품 이름은 아직 정하지 않았습니다.

## 바로 실행하기

Windows에서는 **`실행.cmd`를 두 번 클릭**합니다. 또는 이 폴더에서:

```powershell
npm start
```

브라우저: **http://127.0.0.1:4318**

1. **Figma 화면 가져오기**를 선택하고 **Codex로 연결**합니다.
2. 담당자가 Figma에서 필요한 화면설계서를 드래그로 선택해 저장합니다. 앱의 **보관된 화면 선택하기**에서 필요한 화면을 골라 분석합니다.
3. Codex 요약을 확인하고, AI가 만든 선택지로 모호한 정책에 답합니다. 직접 입력하거나 미정으로 남길 수도 있습니다.
4. **관련 API 찾기**를 누릅니다. 지정한 컨트롤러 폴더에서 AI가 추천한 실제 API를 체크·해제한 뒤 **선택한 API로 테스트 기준 만들기**를 누릅니다.
5. 기준과 요청값을 확인하고 **이 기준으로 테스트 작성·검사하기**를 누릅니다. 프로젝트 설정에는 백엔드 폴더를 지정합니다. 도구가 별도 Spring 테스트 공간과 H2 메모리 DB를 준비하며 서버 주소·쓰기 허용 설정은 필요하지 않습니다.
6. 결과에서 기획 / 실제 / 근거를 비교합니다. **테스트 코드 내려받기**로 실행 가능한 테스트·승인 기준·실행 입력·결과를 ZIP으로 받거나 다시 검사합니다.

**예제로 체험하기**는 별도 공간입니다. 정상 구현은 PASS, 권한 규칙이 빠진 구현은 FAIL이 됩니다. 예제에는 실제 Figma 파일이나 AI 분석이라고 오인할 표시를 붙이지 않습니다.

앱과 실제 HTTP API 검사에는 Node.js 22 이상이 필요합니다. 기존 Java/MockMvc 실험 경로에는 JDK 21이 필요합니다. 첫 테스트 실행 시 Maven 3.9.9를 SHA512 검증 후 `.tools/`에 설치하고 Maven Central에서 테스트 의존성을 내려받습니다. npm 런타임 의존성은 없습니다. 사용자가 테스트 코드를 작성할 필요는 없습니다.

## 실제로 구현한 범위

- 구조화된 Requirement → Condition → API Contract → Scenario, 통합 승인 및 버전 해시
- Figma 원문·답변으로 Codex가 일반 기능의 API·검사안을 제안하고, 승인 뒤 고정 Harness로 실행 가능한 Java 테스트 생성
- 조회·해제·상태 변경 등의 HTTP 요청, JSON Pointer 응답값 비교, 단일 대상 데이터의 존재·소유자·상태 관찰
- 실제 API 발견 단계에서는 컨트롤러·DTO를 읽습니다. 업무 기대값은 원문·답변으로 정하고 실행 직전에 승인 Snapshot을 저장·동결합니다. 기존 Java 구조 분석 경로는 Snapshot 이후 Backend를 읽습니다.
- 제한된 Java 구조 분석 → 고정 Java Harness에 프로젝트 시작 클래스·DB 컬럼 연결
- JUnit 5 / 실제 Spring MVC·Security 필터 / MockMvc / H2 기반 실행
- 실행 전 실제 사용자·소유자·상태·관계 검사, 인증된 MVC 요청의 Actor·Handler 기록
- 실제 HTTP 응답과 DB 상태 관찰에 따른 PASS / FAIL / BLOCKED / UNVERIFIED
- 대상 원본을 수정하지 않는 실행용 복사본, 실행 전후 원본 해시 확인
- Figma 선택 화면 Plugin: 이미지·노드 트리·텍스트·좌표·부모 관계 수집, 프로젝트 연결, 재스캔
- Figma 자동 전송 → 기획 의도 확인 → 통합 승인 (JSON 가져오기는 전송 실패 시 보조 기능)
- 공식 Codex App Server의 ChatGPT 로그인으로 이미지·구조·텍스트 분석, Intent 및 확인 질문 생성
- 승인 명세 Markdown / JSON 내보내기, Notion 새 페이지 생성과 동일 승인 버전 중복 방지
- 행동 중심 한국어 UI, 자동 현재 단계, 실제 작업/예제 분리, 고정 주요 버튼, 결과 전달 복사, 모바일 레이아웃
- 실행 중 새로고침 복구, 승인 후 기준 수정과 재승인, 이전 결과의 버전 구분
- CLI `init`, `verify`, `--feature`, 직접 명세 파일 입력

## 실제 컨트롤러 기반 API 검사 (2026-09-21)

DDD 하위 폴더의 Spring 컨트롤러 매핑과 관련 DTO/record/enum을 읽고 Codex가 Figma와 관련된 API를 추천합니다. 서비스 구현 본문은 AI의 기대값 입력에 포함하지 않습니다. 기본 탐색 범위는 src/main/java이며 프로젝트 설정에서 좁힐 수 있습니다.

선택한 API의 승인 기준을 별도 Spring/MockMvc 테스트로 실행합니다. 실제 컨트롤러·서비스와 H2 메모리 DB를 사용하며 생성·수정·삭제 요청도 실행합니다. 원본 Java 소스는 테스트 공간에 복사하고 원본 설정 파일·resources·운영 DB 접속 정보는 복사하지 않습니다. 요청마다 트랜잭션을 롤백하며 전체 DB는 테스트 프로세스 종료 시 폐기됩니다. 외부 네트워크는 차단합니다. 인증과 계정·레코드 준비가 필요한 항목은 BLOCKED, 외부 연결은 UNVERIFIED입니다. 현재 단일 모듈 Java 21 / Spring Boot 3의 일반 Maven·Groovy Gradle 의존성 선언을 지원합니다. 커스텀 빌드 플러그인·다중 모듈·네이티브 SQL·외부 리소스 초기화는 추가 바인딩이 필요할 수 있습니다.

서버 미실행, 인증 또는 테스트 데이터 부족은 BLOCKED입니다. 테스트 파일은 생성되어 ZIP으로 받을 수 있습니다. DB 내부 상태, 시간 경과, 무작위 분포, 다중 사용자 권한 전체를 응답 일부만으로 PASS 처리하지 않습니다. 프론트엔드 조건과 미검증 정책은 접힌 상세 및 Coverage에 보존합니다.

컨트롤러 탐색은 Java의 일반적인 Spring 매핑을 지원합니다. Kotlin, 동적 경로 상수, 상속/인터페이스에 분리된 복잡한 매핑을 완전하게 해석하는 Java 컴파일러는 아닙니다. 찾은 실제 후보를 사용자가 확인해야 합니다.

검증: npm test / npm run prove / npm run prove:h2. ZIP에는 생성한 Java 테스트·분리된 pom·승인 기준·실행 결과를 넣습니다. 실제 API 응답은 결과의 API 응답 보기에서 확인합니다. 이전 HTTP 실행 기록은 남기지만 새 UI 실행은 H2를 사용합니다. JUnit 종료 코드만으로 전체 PASS를 판단하지 말고 앱의 Evidence/Coverage를 확인하세요.

## 기존 Java/MockMvc 실행 경로의 지원 경계

게시글 삭제 전용 엔진에 더해 **일반 API의 조회·삭제·단일 대상 상태 변경**을 지원합니다. Codex는 Backend를 읽지 않고 원문과 답변에서 API·기대 결과를 제안하며 사용자가 한 번에 승인합니다. GET/POST/PUT/PATCH/DELETE 요청, JSON 객체 본문, 응답 상태·JSON 값, 대상의 존재·소유자·상태를 검사합니다. 경로 변수는 단일 targetId이며 쿼리·새 데이터 생성·여러 레코드 관계·정렬·페이지 분할·실제 로그인/토큰 만료는 미지원입니다. 미지원 원문과 미정 정책도 Coverage에 남습니다.

독립적인 Maven 단일 모듈, 하나의 Spring Boot 시작 클래스, H2 메모리 DB, Spring Security ROLE_USER 테스트 인증이 필요합니다. 대상 테이블은 ID·소유자·상태만으로 Fixture를 구성할 수 있어야 합니다. 임의의 Spring Boot 프로젝트가 설정 없이 모두 동작한다고 보장하지 않습니다. 상위 POM, 멀티모듈, 복잡한 Fixture·인증, 외부 시스템은 후속 지원 대상입니다.

현재 Adapter 생성은 **제한된 구조 분석기와 도구 소유 Harness**를 사용합니다. 실행 가능한 Java를 LLM이 자유롭게 생성·수정하지 않습니다. Experiment B는 잘못된 소스를 읽어도 이 변환기의 Expected가 달라지지 않는다는 증명이며, 자유 형식 LLM 코드 생성의 의미 보존을 검증한 것은 아닙니다.

MockMvc는 실제 Controller와 Security 체인을 호출하지만 네트워크 서버는 기동하지 않습니다. 인증은 정상 사용자 주입 방식이므로 실제 로그인·JWT 발급 검증은 포함하지 않습니다. DB는 매 실행별 H2 메모리 DB입니다. 코드는 복사본에서 실행하지만 **OS 수준의 보안 샌드박스는 아닙니다**. 선택한 프로젝트의 Maven 빌드와 Spring 설정은 실행되므로 신뢰하는 로컬 프로젝트만 연결합니다. 자격 증명 환경변수는 자식 프로세스에 상속하지 않습니다.

대상 Backend의 Production Code는 생성하거나 수정하지 않습니다. `fixtures/*/src/test/java/` 아래 정상·결함 구현은 이번 실험만을 위한 테스트 소스입니다. 도구 자체의 소스는 `lib/`, `server.mjs`, `web/` 등에 있습니다.

## Figma → 질문 → 승인

1. `npm start`로 로컬 서비스를 실행합니다.
2. Figma Desktop 개발 플러그인에서 `figma-plugin/manifest.json`을 등록합니다. Figma가 Plugin ID를 요구하면 개발 플러그인을 새로 만들고 Figma에서 발급한 ID를 manifest에 넣습니다. 배포된 플러그인은 아닙니다.
3. 플러그인을 실행하면 앱의 프로젝트 확인 화면이 열립니다. **이 프로젝트로 연결**을 한 번 누르면 파일별 연결이 저장되어 다음 실행부터 자동 연결됩니다. 연결 코드나 파일 링크를 입력하지 않습니다.
4. Figma에서 필요한 화면설계서들을 드래그로 선택하고 **선택한 화면설계서 저장**을 누릅니다. 완료 후 앱의 **보관된 화면 선택하기**에서 1~6개 설계서를 골라 **선택한 화면으로 기획 확인하기**를 누릅니다. 보관함의 **의도 분석 모델**에서 실제 사용할 Codex 모델도 선택할 수 있습니다.
5. 원문과 Codex 요약을 보고 권한·거절 시 안내 등 기획 의도를 답합니다. HTTP 코드를 직접 고르지 않습니다.
6. **관련 API 찾기 → API 체크 → 선택한 API로 테스트 기준 만들기** 후 검사할 동작을 확인하고 **이 기준으로 테스트 작성·검사하기**를 누릅니다. API·원문·테스트 상세는 펼쳐볼 수 있습니다. 작성 중 새로고침하거나 답변을 바꿔도 오래된 응답으로 새 기준을 덮어쓰지 않습니다.

Figma 계정이 없어도 `examples/figma-scan.json`을 웹에 가져오면 같은 로컬 흐름을 재현할 수 있습니다. 이 파일은 실제 Figma 추출물이 아니라 **명시적인 합성 테스트 데이터**입니다.

## Codex 로그인으로 실제 AI 분석

**OpenAI API 키 입력은 제거했습니다.** 공식 `codex app-server --listen stdio://` 프로세스와 JSON-RPC로 연결합니다. `account/read`로 ChatGPT 로그인 상태를 확인하고, 필요할 때 `account/login/start`의 `chatgpt` 모드로 공식 로그인 화면을 엽니다. 인증 저장·갱신은 Codex 런타임이 담당하며, 이 도구는 OAuth 토큰이나 `auth.json`을 읽거나 복사하지 않습니다. API 키 또는 다른 공급자로 자동 전환하지 않습니다.

이 컴퓨터에서 확인한 버전은 PATH의 CLI `0.144.5`, 실제 연결한 데스크톱 `codex.exe`는 **0.155.0-alpha.2.6**입니다. 실행 파일을 명시하려면 서버를 실행하기 전에 `CODEX_BINARY`를 설정합니다. Windows에서는 `codex.exe`를 먼저 찾고, 더블클릭 실행처럼 PATH에 없으면 설치된 Codex Desktop과 npm의 공식 실행 파일을 탐색합니다. 다른 환경에서는 `codex`를 찾습니다. 런타임별 JSON Schema는 `codex app-server generate-json-schema`로 확인했습니다. 다른 버전 전체에 대한 호환성은 보장하지 않습니다.

- `thread/start`: 별도 임시 작업 디렉터리, ephemeral thread, read-only, 승인 요청 거부, OpenAI provider 고정
- `turn/start`: Figma 노드·텍스트와 `image` 입력, `outputSchema`로 구조화된 결과
- 이미지 최대 6장. 그 이상은 원문은 보존하되 분석 범위 제한을 명시
- 실제 완료 이벤트와 JSON 검증 후에만 Codex 분석 완료 표시
- 로그인 필요 / 사용량 한도 / 런타임 없음 / 일반 분석 실패 구분
- 실패해도 원문 보존 및 다시 분석. 규칙 기반 보관을 AI 성공으로 바꾸지 않음
- AI 해석은 후보로 남기고 사용자의 통합 승인 이후에만 검사 기준으로 사용
- 추가 질문에 답해도 현재 Harness가 없는 조건은 UNVERIFIED로 유지

실제 ChatGPT 로그인으로 합성 이미지·노드·텍스트 분석을 실행했습니다. 근거는 `output/codex-live-proof.json`입니다. 명시적인 테스트 화면 `examples/figma-scan.png`를 사용했으며 실제 Figma 파일 분석으로 주장하지 않습니다. 재현하려면 `node scripts/check-codex-live.mjs`를 실행합니다. 이 명령은 Codex 구독 사용량을 소비합니다.

Figma Desktop에서 개발 플러그인 실행, 실제 파일의 자동 식별, 프로젝트 연결과 재실행 복원을 확인했습니다. Notion 실제 Workspace 생성은 미확인입니다. 신규 OAuth 브라우저 로그인은 이미 로그인된 환경이므로 실제로 재로그인하지 않았습니다. 기존 로그인 재사용과 실제 모델 호출은 확인했습니다. 한도 소진·로그인 만료 오류 분기는 테스트용 응답으로 검증했습니다.

## 실제 Backend 연결

웹의 **프로젝트 설정 → 이 프로젝트에서 검사할 백엔드**에서 경로와 테스트 데이터 컬럼을 지정할 수 있습니다. 또는 Backend 루트에서 이 프로젝트의 `tool.cmd`를 절대 경로로 실행합니다.

```powershell
# 한 번 연결. 자체 프로젝트에 맞게 adapter-profile.json을 작성하세요.
& 'C:\path\to\this-project\tool.cmd' init --profile 'C:\path\to\adapter-profile.json'

# 승인된 READY 기능만 실행
& 'C:\path\to\this-project\tool.cmd' verify
& 'C:\path\to\this-project\tool.cmd' verify --feature 기능ID
```

바인딩 형식은 `fixtures/adapter-profile.json`을 참고합니다. 실제 프로젝트에서는 `createTable: false`로 설정하고 검증용 H2에 테스트 스키마를 준비해야 합니다. 첫 버전은 같은 테이블에 ID·소유자·상태만으로 Fixture를 구성할 수 있는 구조를 지원합니다. 다른 필수 컬럼이 있으면 Fixture 단계가 BLOCKED됩니다. Production 자격 증명을 사용하지 않습니다.

서버 없는 예제 실행:

```powershell
node cli.mjs verify --demo normal
node cli.mjs verify --demo violating
```

종료 코드: `0` 전체 지원 조건 통과, `1` FAIL, `2` BLOCKED/실행 오류, `3` UNVERIFIED/불완전 Coverage. CLI는 사용자 승인된 기준만 실행하며 검증할 기준을 새로 승인하지 않습니다.

## Notion

공통 **연결 설정**에는 **노션 API 키 (Notion Integration 토큰)**만 입력합니다. 프로젝트를 만든 뒤 열리는 **프로젝트 설정**에서 **이 프로젝트의 노션 페이지 링크**를 지정합니다. 이후에도 사이드바의 프로젝트 설정에서 바꿀 수 있습니다. 노션 페이지의 연결 메뉴에 해당 Integration을 연결해야 합니다. **Notion에 보내기**는 기능이 속한 프로젝트의 주소만 사용합니다. 저장 주소가 없는 프로젝트는 전송을 막으며, 과거 공통 주소를 다른 프로젝트에 자동 적용하지 않습니다.

## 기본 Notion API 명세 양식

기존 양식의 제목 순서와 `key / type / description` 열 구조를 내부 기본 양식으로 사용합니다. 제삼자의 원본 페이지 링크와 ID는 설정 화면·API 기본 양식 메타데이터·새 출력 문서에 노출하지 않습니다. 별도의 외부 템플릿 페이지를 생성하지 않았습니다.

- AI 분석 후 사용자가 승인한 API 계약만 문서에 채웁니다. 출력 단계에서는 AI가 Expected나 계약을 다시 결정하지 않습니다.
- Header / Path Variable / Query Param / Request Body는 각각 독립적으로 판단합니다. Body를 쓰더라도 URL에 경로 변수가 있으면 함께 유지합니다.
- 명시적으로 미사용인 항목과 빈 예시를 제거합니다. 정보 누락은 미사용으로 추측하지 않고 ‘미확정’으로 표시합니다.
- 원본의 200 / 400 예시는 승인된 응답 코드로 대체합니다. 204 응답에 JSON 본문을 만들지 않습니다.
- Notion에는 연결 페이지의 DB에 API별 문서를 만듭니다. DB 기본 템플릿의 제목·색상·필드 DB 스키마를 읽어 사용 항목만 채웁니다. 템플릿이 없으면 내장 API 양식을 사용합니다. 기획 근거·검증 범위·시나리오·내부 해시는 Notion 본문에 넣지 않습니다. Markdown은 앱의 검토·내보내기용으로 별도 유지합니다.
- `문서 앞에 추가할 내용`은 제거했습니다. 기존 저장값도 출력에 사용하지 않습니다. 양식 버전이나 게시 대상 변경 후에는 이전 출력 결과를 잘못 재사용하지 않습니다.

내부 계약의 선택적 문서 필드는 `contract.request`의 `headers`, `pathParameters`, `queryParameters`, `body`, `example`과 `contract.responses`입니다. 필드 표는 `{key, type, description}`을 사용합니다. 미사용 배열은 `[]`, 미사용 본문은 `null`, 미확정은 필드 생략으로 구분합니다. 사용자가 직접 JSON이나 프롬프트를 작성하는 흐름은 아닙니다. 현재 실행 엔진이 지원하지 않는 Body/Query/Header/응답 구조가 추가되면 검증 결과는 UNVERIFIED로 남깁니다.

Notion 전송에는 공통 연결 설정의 API 키와 해당 프로젝트 설정의 페이지 링크가 필요합니다. 템플릿 원본에는 쓰지 않습니다. [공식 블록 API](https://developers.notion.com/reference/block)를 사용합니다.

### 선택한 설계서 저장과 화면 보관함

담당자만 개발 플러그인을 설치하고 연결합니다. 프로젝트당 Figma 파일 하나, 현재 페이지에서 직접 선택한 항목들만 수집합니다. 화면설계서의 Frame/Group/Section 전체를 선택하면 내부 화면과 설명·좌표·연결 정보를 통째로 보관합니다. 부모와 자식을 함께 선택하면 자식은 중복 저장하지 않습니다. 선택 밖 컴포넌트나 설명은 수집하지 않습니다. 새 저장이 완료되면 현재 보관함의 범위를 이번 선택으로 갱신하며 이전 기록은 유지합니다. 개발 플러그인의 `enablePrivatePluginApi`로 파일 키와 링크를 자동 전달합니다. 클라우드 키가 없는 문서는 비밀이 아닌 문서 식별값만 pluginData에 저장하며 링크를 만들지 않습니다. 이 대체 식별값은 문서 복제 시 함께 복제될 수 있어 독립 파일 식별 보장은 클라우드 키가 있는 파일에 한정됩니다. 파일명으로 식별하지 않습니다.

- 개발 플러그인의 `devAllowedDomains`와 기본 주소는 **http://localhost:4318**로 통일했습니다. 이전 127.0.0.1 연결 설정은 불러올 때 localhost로 바꿉니다. manifest 수정 후 Figma의 `Import plugin from manifest`에서 같은 파일을 다시 등록하세요.
- 한 번에 선택한 최대 2,000개 항목을 한 화면씩 수집·전송하고 저장 응답을 기다립니다. 모든 이미지를 플러그인 메모리에 모으지 않습니다. 수집본 이미지 합계는 1GB, 개별 이미지와 노드 구조에도 제한이 있으며 초과 시 누락시키지 않고 오류로 알립니다. 보관용 노드 한도는 화면당 100,000개이며 AI 선택 분석에는 기존 4,000개 제한이 별도로 적용됩니다.
- 화면별 업로드가 모두 끝난 뒤 완료본을 원자적으로 공개합니다. 전송 실패 시 이전 완료본을 유지하고 이어서 전송할 수 있습니다. 최신 완료본과 충돌하는 오래된 동기화는 덮어쓰지 않습니다.
- 플러그인과 프로젝트 홈에서 수신 개수를 확인할 수 있습니다. 완료 후 **앱에서 보관된 화면 보기 →**를 누르면 연결된 프로젝트의 보관함이 열립니다. JSON 파일을 따로 가져올 필요는 없습니다. 동기화는 원문 보관이며, AI 분석은 앱에서 화면을 선택한 뒤 시작합니다.
- 화면 내용 해시로 디스크 중복 저장을 줄입니다. 현재는 재탐색과 업로드 자체를 생략하지 않습니다.
- 같은 ID의 화면 이름 변경을 추적하고, 새 수집 범위에서 사라진 화면을 기록합니다. 선택 범위를 바꿔 빠진 화면과 Figma에서 실제 삭제한 화면을 동일 원인이라고 단정하지 않습니다.
- 분석에는 선택한 설계서 내부의 설명을 넣으며 범위를 화면에 표시합니다. 설명이 설계서 밖에 있으면 함께 선택해야 합니다. 과거 페이지 전체 수집본은 당시의 설명 범위를 그대로 유지합니다. 완벽한 단일 시점 복제본을 보장하지 않습니다.
- 새 원문이 생겨도 기존 승인·실행 근거는 보존합니다. 실제 연결된 화면/설명이 변경된 작업만 ‘새 화면 검토 필요’로 표시하고 새 승인·실행 전에 검토를 요구합니다.
- 저장: `.local/screen-library/`. AI 실행 및 Backend 검사와 분리된 저장 모듈이며 승인 기준의 내용에는 접근하지 않습니다.

**현재 구현은 로컬 보관함 첫 단계입니다.** 팀 로그인·프로젝트 접근 권한·동기화 담당자 권한·중앙 서버 배포·여러 컴퓨터 간 보관함 연결은 아직 없습니다. 현재 로컬 서버를 외부에 공개해서 팀 서버로 사용하지 않습니다. 중앙 서버는 원문 공유, 각 로컬 실행기는 Codex 분석과 Backend 검사를 담당하는 후속 구조가 적절합니다. 저장된 원문 조회에는 Figma API 호출이 없지만 수집 시간·전송량·저장 공간·AI 사용량 제한은 남습니다.

개별 선택 전송 실패 시에만 JSON 저장 버튼을 제공합니다. 웹의 **플러그인에서 전송에 실패했어요**에 대체 가져오기를 숨겼습니다. 일반 사용자는 파일 가져오기를 거치지 않습니다.

## 연결과 프로젝트 설정

- 공통 연결 설정: Codex와 노션 API 키. 프로젝트별 설정: 노션 저장 페이지와 백엔드 폴더·테스트 DB 연결.
- 화면 보관함은 프로젝트 첫 화면의 ‘보관된 화면 선택하기’로 엽니다. 예제 체험은 왼쪽 프로젝트 추가 위에 한 번만 표시합니다.
- Figma 최초 연결은 앱에서 프로젝트를 한 번 확인합니다. 연결 URL에는 접근 토큰이 없으며, 승인 전에는 프로젝트 목록을 읽거나 원문을 전송할 수 없습니다. 발급한 연결은 선택 프로젝트와 파일에 한정합니다. 미확인 요청은 3분 뒤 만료됩니다.
- 플러그인의 로컬 주소는 접힌 고급 설정 안에 있습니다. 개발 실행 주소는 localhost:4318로 고정되어 수정할 필요가 없습니다.
- manifest의 `id`는 로컬 개발용 고정 식별자입니다. 이를 제거하면 Figma clientStorage를 사용할 수 없어 자동 재연결이 동작하지 않습니다. Community 배포 시에는 Figma가 발급한 정식 ID를 사용해야 합니다.
- 연결 비밀값은 Figma clientStorage와 앱의 로컬 저장소에만 저장합니다. 문서 pluginData에는 토큰을 저장하지 않습니다.

### Codex 모델과 분석 오류

연결 설정 또는 보관된 화면 선택 창의 **의도 분석 모델 → 분석 모델 저장**에서 선택합니다. 설치된 공식 Codex 런타임이 반환한 이미지 지원 모델만 표시합니다. 기본값의 실제 이름과 분석 결과에 사용한 모델도 확인할 수 있습니다. 설정 변경은 다음 분석부터 적용됩니다.

실패하면 원문을 유지한 채 원인별 안내와 재분석을 제공합니다. 오류 상세의 진단 번호는 `.local/analysis-logs/<번호>.json`에 대응합니다. 로그인·사용량·통신·시간 초과·응답 형식 오류를 구분하며 유료 API로 자동 전환하지 않습니다. 분석 완료와 실제 Backend 검증 PASS는 다른 상태입니다.

### 서버 정책 확인과 보관함 정리

- 의도 확인에서는 서버가 허용·거절·저장할 동작만 묻습니다. 표시 문구나 화면 이동 질문은 제외합니다. 추가 설명을 강제로 쓰지 않으며, 미정인 답은 미정으로 저장합니다.
- 현재 테스트 실행기가 지원하지 않는 기능은 정책만 보관합니다. API 계약을 임의 생성하지 않고 검사 승인도 하지 않습니다.
- **보관된 화면 선택하기 → 체크박스로 선택 → 선택한 화면 삭제**로 목록을 정리합니다. **삭제한 화면 · 복구하기 → 복구**로 되돌릴 수 있습니다. Figma 원본과 기존 분석·승인 기록은 그대로입니다.
- 삭제는 복구 가능한 목록 제외이므로 디스크 원본 파일을 영구 삭제하거나 저장 용량을 줄이는 기능은 아닙니다. 같은 화면을 재동기화해도 삭제 상태를 유지합니다. Figma 수집 범위에서 빠진 화면은 다시 수집해야 복구 목록에 나타납니다.


### H2 테스트 데이터와 Notion 자동 저장

- 로그인 API는 테스트 트랜잭션 안에서 H2 계정을 준비한 다음 실제 컨트롤러·서비스를 호출합니다. 지원하는 계정 팩토리는 JPA 엔티티의 `createLocalUser(String, String, String, String)`이며 실제 `PasswordEncoder`로 요청 비밀번호를 암호화합니다. 형식이 잘못된 이메일 요청은 별도 정상 이메일 계정을 준비하고 요청 자체는 바꾸지 않습니다.
- 이 fixture는 로그인 성공·입력 형식 검사의 기존 계정 사전조건을 준비합니다. 비밀번호가 일치하지 않거나 미가입 계정인 조건은 이 fixture로 덮어쓰지 않고 BLOCKED로 남깁니다. 다른 엔티티/관계/인증 방식의 범용 자동 데이터 생성은 아직 지원하지 않습니다.
- JPA `persist/flush`와 실제 조회로 준비를 확인하고, 요청 후 롤백된 행 수를 Evidence에 기록합니다. 대상 백엔드의 Production Code와 승인 Expected는 수정하지 않습니다. 재현: `npm run prove:fixtures`.
- 노션 API 키와 프로젝트의 **페이지 또는 DB 링크**가 설정되어 있으면 승인·검사 시작 시 API별 행을 자동 작성합니다. 페이지에 DB가 없으면 생성하며, 하나 있으면 사용합니다. 여러 DB가 있으면 사용할 DB 링크를 안내합니다. 같은 승인 버전의 재전송은 이어 쓰고 문서를 중복 생성하지 않습니다.
- 상단에 저장 중·완료·실패와 ‘Notion 명세 열기’/‘다시 보내기’를 표시합니다. Notion 오류는 H2 검사를 중단하지 않습니다. 동일 승인 버전과 저장 위치의 재검사는 기존 문서를 재사용합니다. 미승인 내용과 예제는 자동 발행하지 않습니다.

### API 목록과 버전 관리 (2026-09-22)

- 목록은 METHOD(메서드별 색상) · 이름(기능명) · URL · 상태 순서입니다. 상세 문서의 필드 표는 key · type · description 순서입니다. 상태의 초안/명세 작성됨은 문서 작성 상태이며 테스트 PASS가 아닙니다. 미정 필드나 응답 계약이 있으면 초안으로 남깁니다.
- 기존 DB의 기본 템플릿과 사용자 작성 행은 보존합니다. 이전에 도구가 잘못 생성한 기능 단위 하위 문서는 이 작업에서만 확인 후 휴지통으로 옮겼습니다.
- 새 검사안은 컨트롤러·DTO의 요청 필드도 승인 전에 포함합니다. 예전 승인 명세에 없는 응답값을 현재 코드에서 가져와 기대값으로 보충하지 않습니다.
- Requirement·API Contract·Scenario는 변경된 항목만 독립적으로 버전을 올립니다. 요구사항 근거 상태와 승인 대기/승인됨/제외됨을 구분합니다. 승인 전 상세에서 잘못 읽은 해석을 제외할 수 있고, 그 조건은 미검증 Coverage에 남습니다.
- 같은 프로젝트의 동일 질문에 승인 답변이 있으면 의도 확인의 선택지로 보여 줍니다. 충돌 답변은 모두 보여 주며 사용자가 고르기 전에는 적용하지 않습니다.
- CLI의 controller-api 검증도 앱과 같은 H2 실행 경로를 사용합니다. 코드만 바뀌면 같은 승인 기준을 다시 실행하고, 현재 API 경로와 메서드가 사라지거나 모호하면 BLOCKED로 남깁니다.

### AI 상세 API 문서

- 승인한 컨트롤러 API를 Notion에 보낼 때 선택한 Codex 모델이 1~2문장의 동작 설명과 요청·응답 필드 설명을 작성합니다. DTO의 제네릭·중첩 구조를 펼치며 요청/반환 JSON 구조 예시도 제공합니다.
- 문서용 보충 설명은 승인된 검증 기준과 별도로 저장합니다. 현재 DTO의 필드·검증 어노테이션이 테스트 Expected를 덮어쓰지 않습니다. 반환 DTO만으로 HTTP 상태·업무 오류 코드·토큰 유효기간 등을 확정하지 않습니다.
- 모든 자동 예시 값은 가상 데이터입니다. 실제 응답의 인증 토큰이나 참고 페이지의 계정 정보를 복사하지 않습니다. 동작 설명은 컨트롤러 선언에 근거하며 외부 API 실행 완료를 뜻하지 않습니다.
- 같은 API 행의 링크를 유지하여 상세 내용을 갱신합니다. 새 본문 작성을 마친 뒤 도구가 관리하던 이전 블록만 휴지통으로 옮기며 사용자 추가 블록은 보존합니다. 작성 중 오류가 발생하면 재전송으로 이어 씁니다.
