# 구현 규칙 보충안

기존 기획안의 제품 방향과 기능 범위는 유지한다.

아래 규칙은 Verification Engine 구현 시 반드시 지켜야 한다.

## 1. Scenario와 Test Adapter의 책임 분리

Verification Scenario는 **무엇을 검증할지**를 결정한다.

Test Adapter는 **현재 프로젝트에서 해당 Scenario를 어떻게 실행할지**만 결정한다.

Test Adapter는 Scenario의 의미, 기대 결과, 사전조건을 변경할 수 없다.

---

## 2. Scenario는 구조화한다

Verification Scenario는 단순 자연어만 저장하지 않는다.

최소한 다음 요소를 구조화한다.

* Actor
* Actor State
* Target
* Actor-Target Relation
* Preconditions
* Action
* Expected Response
* Expected Data State

자연어 Given / When / Then은 구조화된 Scenario를 사람이 읽기 쉽게 표현한 형태로 사용한다.

---

## 3. Scenario 의미를 보호한다

Test Adapter 생성 및 자동 수정 과정에서 다음 의미는 변경할 수 없다.

* Actor의 역할과 상태
* Target의 종류와 상태
* Actor와 Target의 관계
* Preconditions
* 수행해야 하는 Action
* Expected Response
* Expected Data State

프로젝트 구조에 맞게 변경 가능한 것은 구현 방법뿐이다.

---

## 4. Verification Harness와 AI Adapter를 분리한다

가능한 범위에서 테스트 전체를 AI가 자유롭게 작성하지 않는다.

Verification Harness는 도구가 통제한다.

Verification Harness가 담당하는 영역:

* Scenario 실행 순서
* Precondition 검사
* Action 실행
* Response 수집
* 데이터 상태 관찰
* Assertion
* Result 판정

AI Adapter가 담당하는 영역:

* Fixture 생성
* 인증 객체 구성
* Repository 연결
* 프로젝트별 API 호출 연결
* 프로젝트별 객체 생성 방식

AI가 검증 기준 자체를 자유롭게 수정할 수 없도록 한다.

---

## 5. 실행 전 Precondition을 검증한다

Action을 실행하기 전에 Structured Scenario의 Preconditions가 실제 테스트 환경에서 충족되었는지 확인한다.

Precondition을 검증하지 못했거나 충족시키지 못한 상태에서는 Business Result를 판정하지 않는다.

---

## 6. 대조 Scenario를 사용한다

가능한 Business Rule은 Positive Scenario와 Negative Scenario를 함께 구성한다.

하나의 실패 Scenario만 통과했다는 이유로 해당 Business Rule 전체를 검증했다고 판단하지 않는다.

---

## 7. Requirement를 검증 가능한 Condition으로 분해한다

하나의 Requirement 안에 여러 독립적인 조건이 존재한다면 내부적으로 검증 가능한 Condition으로 분해한다.

각 Condition에는 필요한 Verification Scenario가 연결되어야 한다.

Scenario가 생성되지 않은 Condition도 Coverage 계산에서 제외하지 않는다.

---

## 8. Coverage는 Condition과 Scenario를 기준으로 계산한다

생성된 Scenario만 기준으로 Coverage를 계산하지 않는다.

승인된 Requirement가 요구하는 모든 Condition을 기준으로 검증 범위를 계산한다.

필수 Scenario가 모두 검증되지 않았다면 Requirement 전체를 PASS로 표시하지 않는다.

---

## 9. 실행 결과의 기본 단위는 Scenario다

각 Scenario는 독립적으로 다음 상태 중 하나를 가진다.

* PASS
* FAIL
* BLOCKED
* UNVERIFIED

Requirement는 Scenario 결과를 집계하여 Coverage 상태만 제공한다.

---

## 10. PASS 판정 규칙

PASS는 다음 조건을 모두 만족한 경우에만 가능하다.

* 승인된 Scenario를 사용했다.
* Preconditions가 정상적으로 충족되었다.
* Action이 실제로 실행되었다.
* 필요한 Observation을 모두 수행했다.
* 실제 결과가 Expected Result와 일치했다.

단순히 특정 HTTP Status가 반환되었다는 이유만으로 PASS 처리하지 않는다.

---

## 11. FAIL 판정 규칙

FAIL은 승인된 Scenario의 Preconditions가 정상적으로 구성되고 Action도 실행된 상태에서 실제 Backend 동작이 Expected Result와 다른 경우에만 사용한다.

---

## 12. BLOCKED 판정 규칙

실행 환경 또는 Test Adapter 문제 때문에 Scenario의 Business Result를 판정할 수 없는 경우 BLOCKED로 처리한다.

AI가 실행 실패 원인을 추측하여 FAIL로 승격하지 않는다.

---

## 13. UNVERIFIED 판정 규칙

다음과 같이 검증 기준 자체가 부족하거나 현재 자동화 범위 밖인 경우 UNVERIFIED로 처리한다.

* Requirement 미확정
* Scenario 미생성
* Scenario 미승인
* 현재 지원하지 않는 Behavior
* 필요한 Observation을 자동화할 수 없음

---

## 14. Result에는 Evidence를 남긴다

각 Scenario 실행 결과에는 판정 근거를 남긴다.

최소 기록 항목:

* Verification Snapshot
* Precondition 검사 결과
* 실제 Actor
* 실제 Target
* Actor-Target Relation
* 실행된 Action
* 실제 Response
* 실행 전 데이터 상태
* 실행 후 데이터 상태
* Mock Boundary
* Failure Stage
* Execution Log

AI의 설명이 아니라 실제 실행 Evidence를 판정 근거로 사용한다.

---

## 15. AI가 원인을 추측해서는 안 된다

실제 실행 결과만으로 어떤 Business Rule이 작동했다고 확신할 수 없는 경우 PASS로 처리하지 않는다.

원인을 확인할 근거가 부족하면 BLOCKED 또는 UNVERIFIED로 남긴다.

---

## 16. CONFIRMED에는 근거가 필요하다

CONFIRMED Requirement에는 구체적인 Evidence Source를 연결한다.

최소한 다음 정보를 추적할 수 있어야 한다.

* Scan
* Figma Node 또는 해당 범위
* 추출된 텍스트 또는 Visual Context

단순히 `origin = figma`만 저장하지 않는다.

---

## 17. Evidence보다 강한 Requirement를 CONFIRMED 처리하지 않는다

Figma에서 직접 확인 가능한 정보와 AI가 해석해서 만든 Business Requirement를 구분한다.

Evidence가 직접 증명하지 않는 내용은 INFERRED 또는 UNKNOWN으로 처리한다.

---

## 18. Requirement, API Contract, Scenario를 각각 버전 관리한다

다음 세 요소는 독립적으로 버전을 가진다.

* Business Requirement
* API Contract
* Verification Scenario

Scenario에는 자신이 어떤 Requirement Version과 API Contract Version을 기준으로 만들어졌는지 기록한다.

---

## 19. Verification Snapshot을 고정한다

검증 시작 시 다음 기준을 하나의 Snapshot으로 고정한다.

* Requirement Version
* API Contract Version
* Scenario Version
* Backend Code 상태

검증 중 최신 Requirement나 Contract로 자동 변경하지 않는다.

---

## 20. 변경 시 재검토 규칙을 둔다

Business Requirement가 변경되면 관련 API Contract와 Scenario의 영향을 다시 확인한다.

API Contract가 변경되면 관련 Scenario를 다시 검토한다.

Scenario 자체가 변경되면 새로운 Version을 생성한다.

영향받은 Feature는 재승인 전까지 READY 상태를 유지하지 않는다.

---

## 21. 과거 PASS와 현재 상태를 분리한다

과거 Version에서 발생한 PASS는 기록으로 보존한다.

하지만 Requirement, Contract 또는 Scenario Version이 변경되면 과거 PASS를 현재 Version의 검증 결과로 사용하지 않는다.

---

## 22. 통합 승인 UX를 사용한다

Business Requirement, API Contract, Verification Scenario는 내부적으로 별개의 데이터로 관리한다.

하지만 사용자에게 세 번의 별도 승인 절차를 요구하지 않는다.

Feature 단위의 하나의 검토 화면에서 함께 보여주고 한 번에 승인한다.

승인 시 어떤 Version 조합이 승인되었는지 기록한다.

---

## 23. `tool verify`의 검증 범위를 명확히 한다

`tool verify`는 프로젝트의 모든 Feature를 자동으로 검사하지 않는다.

검증 대상으로 지정된 READY Feature의 승인 Snapshot만 실행한다.

검증 시작 전에 대상 Feature와 기준 Version을 명확하게 고정한다.

특정 Feature만 검증할 수 있는 선택 기능을 제공한다.

---

## 24. Test 자동 수정 범위를 제한한다

AI가 자동으로 수정할 수 있는 영역:

* Import
* Package
* Fixture 구현 방식
* 객체 생성 방식
* Repository 연결 방식
* 인증 객체 생성 방식
* 프로젝트별 API 호출 코드

AI가 수정할 수 없는 영역:

* Scenario의 의미
* Actor와 Target의 관계
* Preconditions
* Action
* Expected Response
* Expected Data State
* Assertion의 의미

---

## 25. Behavior Verification의 범위를 초기에는 제한한다

첫 버전에서는 의미 보존과 실행 환경을 통제하기 쉬운 Behavior를 우선 지원한다.

우선 지원:

* 권한
* 중복
* 단순 상태 조건
* 단순 CRUD Business Rule
* API Contract

후순위:

* 복잡한 Transaction
* Concurrency
* Async Processing
* Message Queue
* Distributed Transaction
* 복잡한 외부 시스템 연동

---

## 26. Experiment A 규칙

동일한 승인 Scenario와 동일한 생성 Test를 정상 구현과 실제 정책 위반 구현에 각각 실행한다.

정상 구현과 정책 위반 구현을 구별할 수 있어야 한다.

---

## 27. Experiment B 규칙

동일한 승인 Scenario를 기준으로 서로 다른 Backend 구현을 각각 분석하여 Test Adapter를 생성한다.

Backend 구현이 다르더라도 다음 의미는 동일하게 유지되어야 한다.

* Actor
* Actor State
* Target
* Actor-Target Relation
* Preconditions
* Action
* Expected Result

잘못된 구현을 분석한 결과 Scenario의 의미가 변경되면 Experiment B 실패로 판단한다.

---

## 28. Experiment B의 합격 기준

Experiment B는 다음 조건을 모두 만족해야 한다.

* Scenario 의미 보존
* Preconditions 의미 보존
* Expected Result 보존
* 정상 구현에 대한 올바른 판정
* 실제 정책 위반 구현에 대한 올바른 판정
* Adapter 오류와 Backend 오류의 구분

---

## 29. 첫 기술 완료 기준

전체 Web, Figma, Notion 기능을 완성하기 전에 하나의 단순한 Business Rule을 대상으로 Verification Engine의 Vertical Slice를 먼저 완성한다.

완료 기준:

* Structured Scenario를 입력할 수 있다.
* Test Adapter를 생성할 수 있다.
* Preconditions를 검사할 수 있다.
* 실제 Backend를 실행할 수 있다.
* PASS / FAIL / BLOCKED / UNVERIFIED를 구분할 수 있다.
* 정상 구현과 실제 정책 위반 구현을 구별할 수 있다.
* 잘못된 구현을 분석해도 Scenario의 의미가 유지된다.

이 기준을 만족한 이후 Figma 분석과 Notion 연동을 연결한다.

---

## 30. 핵심 원칙

Verification Engine 전체에서 다음 원칙을 유지한다.

> **AI는 검증 기준을 결정하지 않는다.**

> **AI는 승인된 검증 기준을 현재 프로젝트에서 실행 가능한 형태로 연결한다.**

> **검증 결과는 AI의 해석보다 실제 실행 Evidence를 우선한다.**

> **현재 Backend 구현은 테스트의 정답이 될 수 없다.**
