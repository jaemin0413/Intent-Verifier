# 1. 프로젝트 개요

## 한 줄 정의

Figma에서 기능과 기획 의도를 AI가 분석하고, 모호한 부분을 사용자에게 질문하여 요구사항을 확정한 뒤, API 명세와 검증 시나리오를 생성하고 현재 백엔드 구현이 해당 의도를 만족하는지 자동 테스트하는 개발 지원 도구.

## 핵심 가치

이 프로젝트의 핵심은 테스트 코드를 많이 만드는 것이 아니다.

> **현재 구현이 잘못되어 있어도 그 구현을 정답으로 받아들이지 않고, 사전에 합의된 기획 의도를 기준으로 잘못되었다고 판정하는 것**

이 가장 중요한 가치다.

---

# 2. 해결하려는 문제

## 2.1 Figma를 충분히 확인하지 않고 개발

백엔드 개발자가 Figma의 전체 기능 흐름과 세부 요구사항을 충분히 확인하지 않은 채 구현할 수 있다.

이 경우 코드는 정상적으로 동작하지만 실제 기획 의도와 다른 기능이 만들어질 수 있다.

---

## 2.2 AI를 이용해 잘못된 요구사항을 빠르게 구현

AI를 활용하면 구현 속도는 빨라진다.

그러나 처음부터 요구사항을 잘못 이해했다면 다음 상황도 가능하다.

```text
잘못 이해한 요구사항
        ↓
AI를 이용한 빠른 구현
        ↓
정상 동작하는 코드
        ↓
현재 코드를 기준으로 생성한 테스트
        ↓
PASS
```

결과적으로 코드와 테스트 모두 정상인데 실제 기획과는 다른 상태가 발생할 수 있다.

---

## 2.3 API 명세 관리 누락

Notion에서 API 명세를 관리하더라도 다음 문제가 발생할 수 있다.

```text
명세 작성 누락

구현 이후 명세 미수정

기획과 API 명세 불일치

작성자마다 다른 문서 품질
```

따라서 다음 요소를 하나의 흐름으로 연결한다.

```text
Figma

↓

Business Requirement

↓

API Contract

↓

Verification Scenario

↓

Backend Implementation

↓

Verification
```

# 3. 적용 범위

초기 버전은 다음 상황을 대상으로 한다.

> **기존 Spring Boot 프로젝트에서 새로 개발하거나 명시적으로 변경하는 기능**

이미 운영 중인 모든 API를 한꺼번에 분석하여 기존 계약과 요구사항을 복원하는 것은 목표로 하지 않는다.

# 4. 가장 중요한 설계 원칙

검증의 정답은 Backend Code를 읽기 전에 결정한다.

```text
Figma 분석

↓

Business Requirement 확정

↓

API Contract 확정

↓

Verification Scenario 확정

────────────────────────────
      검증 기준 고정
────────────────────────────

↓

Backend Code 분석

↓

현재 프로젝트에 맞는 Test Adapter 생성

↓

Test 실행

↓

Result
```

Backend Code는

> **무엇이 정답인지**

를 알려주는 자료가 아니다.

Backend Code는

> **이미 정해진 Scenario를 현재 프로젝트에서 어떻게 실행할 것인지**

를 알아내기 위해 읽는다.


# 12. 분석 범위 표시

AI는 무엇을 읽었는지를 사용자에게 보여준다.

예:

```text
이번 Scan에서 분석한 범위

✓ 게시글 상세
✓ 게시글 삭제 Modal

현재 Scan에서 확인하지 못한 영역

- 관리자 게시글 관리
- 탈퇴 회원 게시글 정책
```

중요한 원칙:

> Unknown이 없다는 것은 모든 요구사항을 찾았다는 의미가 아니다.

AI가 요구사항의 존재 자체를 발견하지 못했을 가능성도 있기 때문에 분석 범위를 항상 함께 보여준다.

# 13. Evidence Status

Figma에서 추출한 정보는 세 가지 상태로 구분한다.

## CONFIRMED

제공된 Figma Context에서 직접 확인했다.

```text
삭제 버튼이 존재한다.
```

## INFERRED

명시되어 있지는 않지만 AI가 정황상 추론했다.

```text
작성자만 삭제할 가능성이 있다.
```

## UNKNOWN

현재 정보만으로 판단할 수 없다.

```text
다른 사용자 삭제 요청을 어떤 정책으로 처리하는가?
```

---

# 14. Approval Status

Evidence와 실제 검증 기준을 분리한다.

각 Requirement에는 별도의 Approval Status를 둔다.

```text
PENDING

APPROVED

REJECTED
```

예:

```yaml
description:
  작성자가 아닌 사용자는 게시글을 삭제할 수 없다.

evidence_status:
  INFERRED

approval_status:
  APPROVED

origin:
  user_answer
```

AI가 그럴듯하게 추론했다고 해서 자동으로 테스트 기준이 되지 않는다.

---

# 15. 질문 순서

질문에서도 Business Requirement와 API Contract를 분리한다.

잘못된 질문:

```text
다른 사람이 삭제하면

403인가요?
404인가요?
```

이는 이미

> 다른 사람은 삭제할 수 없다

를 전제한다.

따라서 먼저 Business Requirement를 묻는다.

```text
게시글은 누가 삭제할 수 있나요?

○ 작성자만
○ 작성자 + 관리자
○ 로그인 사용자 모두
○ 별도 정책
```

그다음 필요한 경우 API Contract를 묻는다.

```text
권한 없는 사용자의 요청은 어떻게 응답할까요?

○ 403
○ 404
○ 프로젝트 기존 정책 적용
○ 별도 정책
```

# 16. AI 질문 우선순위

모든 모호한 내용을 사용자에게 묻지 않는다.

질문 중요도는 다음을 기준으로 판단한다.

```text
잘못 판단했을 때의 영향

×

현재 불확실성

×

현재 검증에 필요한 정도
```

권한, 데이터 변경, 중복, 상태 전이처럼 실제 기능 결과를 바꾸는 사항을 우선한다.

이미 프로젝트에서 결정된 정책은 재사용한다.

예:

```text
현재 Project에서는

권한 부족 → 403

을 기본 정책으로 사용하고 있습니다.
```

기존 정책과 현재 기능이 충돌하면 자동 적용하지 않고 사용자에게 충돌을 알려준다.

# 18. Intent Spec

확정된 요구사항은 내부적으로 구조화한다.

예:

```yaml
feature: post-delete

requirements:

  - id: REQ-POST-001

    description:
      사용자는 자신의 게시글을 삭제할 수 있다.

    evidence_status:
      CONFIRMED

    approval_status:
      APPROVED

    origin:
      figma


  - id: REQ-POST-002

    description:
      다른 사용자는 게시글을 삭제할 수 없다.

    evidence_status:
      INFERRED

    approval_status:
      APPROVED

    origin:
      user_answer
```

Intent Spec은 이후 모든 작업의 기준이다.

# 19. Business Requirement와 API Contract

둘을 별개의 데이터로 관리한다.

## Business Requirement

```text
작성자만 자신의 게시글을 삭제할 수 있다.
```

## API Contract

```text
DELETE /posts/{postId}

Success
204 No Content

Permission Denied
403 Forbidden
```

AI는 Requirement를 바탕으로 API Contract를 제안할 수 있다.

그러나 제안한 Contract가 자동으로 정답이 되지는 않는다.

# 20. Notion API 명세

승인된 API Contract는 Notion에 출력한다.

MVP에서 지원하는 방식:

```text
Intent 기본 Template

또는

사용자가 직접 입력한 Template
```

기본 Template:

```text
API Name

Description

Endpoint

Method

Authentication

Request

Response

Business Rules

Error Cases

Related Figma

Verification Scenarios
```

MVP에서는 Notion → Intent Spec의 양방향 동기화를 지원하지 않는다.

Notion은 우선 출력 대상이다.

# 21. Verification Scenario

Business Requirement와 API Contract가 확정되면 Backend Code를 보기 전에 Scenario를 생성한다.

예:

```text
REQ-POST-002

Given

사용자 A가 정상 상태의 계정이다.
사용자 B도 정상 상태의 계정이다.
A가 작성한 게시글이 존재한다.
B는 게시글 작성자가 아니다.

When

B가 해당 게시글 삭제 API를 호출한다.

Then

403 Forbidden을 반환한다.
게시글은 삭제되지 않는다.
```

이 단계에서 테스트의 의미를 확정한다.

---

# 22. Structured Verification Scenario

Scenario는 단순 자연어만 저장하지 않는다.

테스트 생성 과정에서 의미가 변하지 않도록 최소한 다음 구조를 가진다.

```yaml
scenario:
  actor:
    user: B
    state: normal_authenticated_user

  target:
    resource: post
    owner: A
    exists: true

  relation:
    actor_is_owner: false

  action:
    type: delete
    api: DELETE /posts/{postId}

  expected:
    status: 403
    target_exists_after_action: true
```

자연어 Given / When / Then은 이 데이터를 사람이 읽기 쉽게 표현한 것이다.

---

# 23. Scenario 의미 보호

AI가 Test Code를 생성하거나 수정할 때 다음 의미는 바꿀 수 없다.

```text
B와 A는 다른 사용자다.

B는 정상적인 인증 사용자다.

게시글은 A의 소유다.

게시글은 요청 전에 존재한다.

B가 삭제 요청을 한다.

Expected Status는 403이다.

게시글은 요청 이후에도 존재한다.
```

반면 다음과 같은 구현 방법은 프로젝트 코드에 맞게 변경할 수 있다.

```text
User 생성자

Fixture Factory

DB 저장 방식

Spring Security 인증 객체 생성 방식

Test package

Repository 조회 코드
```

핵심 원칙:

> **Given을 유지하는 것이 아니라 Given의 의미를 유지한다.**

# 24. Test Adapter Generation

AI는 테스트를 처음부터 자유롭게 창작한다기보다,

> **승인된 Scenario를 현재 프로젝트에서 실행 가능한 Test Code로 변환**

한다.

이를 Test Adapter Generation으로 정의한다.

```text
Approved Scenario

↓

Backend 구조 분석

↓

프로젝트에 맞는 Fixture / Auth / API 호출 연결

↓

Executable Test
```

---

# 25. Backend Code 분석

코드 분석의 목적은 Test Adapter 생성이다.

AI가 Backend에서 파악할 수 있는 정보:

```text
Controller 위치

Service 위치

DTO

Domain

Repository

Authentication 구성

Fixture 생성 방식

기존 Test 구조

Build 설정
```

코드에서 결정하면 안 되는 것:

```text
누가 기능을 사용할 수 있는가

무엇이 성공인가

무엇이 실패인가

어떤 Status가 정답인가

어떤 데이터 상태가 올바른가
```

# 26. 검증 대상 Business Rule 실행

검증하려는 업무 규칙을 실제로 수행하는 객체는 가능한 한 Mock하지 않는다.

예:

```text
작성자만 게시글 삭제 가능
```

을 검증하면서 `PostService` 자체를 Mock하여 강제로 403을 발생시키면 실제 권한 검증이 아니다.

따라서 원칙은:

> **검증하려는 업무 규칙이 위치한 계층은 실제로 실행한다.**

외부 시스템이나 검증 범위 밖의 의존성은 Mock할 수 있다.

어떤 경계를 Mock했는지는 결과에 표시한다.

---

# 27. 대조 Scenario

단일 실패 Scenario만으로 Business Rule을 검증하지 않는다.

가능한 경우 Positive / Negative Scenario를 함께 만든다.

예: 권한

```text
Positive

작성자 A가 자신의 게시글 삭제
→ 성공

Negative

사용자 B가 A의 게시글 삭제
→ 실패
```

예: 중복

```text
Positive

새 이메일 회원가입
→ 성공

Negative

기존 이메일 회원가입
→ 실패
```

이를 통해 CSRF, 인증 구성 오류 등 다른 이유로 요청이 차단된 것을 Business Rule 검증 성공으로 오판할 가능성을 줄인다.

# 28. MVP에서 공식 지원하는 Behavior

초기에는 모든 Backend 규칙을 자동 검증하려 하지 않는다.

우선 다음과 같이 통제하기 쉬운 유형에 집중한다.

```text
권한

중복

단순 상태 조건

간단한 CRUD Business Rule

API Contract
```

다음은 후순위로 둔다.

```text
복잡한 Transaction Rollback

Concurrency

Async Processing

Message Queue

Distributed Transaction

복잡한 외부 시스템 연계
```

# 29. Test 자동 수정

생성된 Test가 컴파일되지 않거나 실행 환경에 맞지 않을 경우 AI가 수정할 수 있다.

수정 가능:

```text
import

package

Fixture 생성 방식

Repository 저장 방식

인증 객체 생성 방식

Method 호출 방식
```

수정 금지:

```text

Actor와 Resource 관계

Precondition 의미

Action

Expected Status

Expected 데이터 상태

Assertion 의미
```

# 30. 검증 결과

Scenario 실행 결과는 네 가지로 구분한다.

## PASS

승인된 Scenario를 정상적으로 실행했고 Expected Result와 일치했다.

## FAIL

사전조건이 정상적으로 구성된 상태에서 실제 결과가 Expected와 다르다.

## BLOCKED

테스트 실행 환경이나 Test Adapter 구성 문제로 검증하지 못했다.

예:

```text
Build 실패

Test DB 연결 실패

Fixture 구성 실패

Authentication 구성 실패
```

## UNVERIFIED

검증 기준 자체가 없거나 현재 지원 범위 밖이다.

예:

```text
Requirement 미확정

Scenario 미승인

현재 지원하지 않는 Business Rule
```

# 31. Scenario 중심 결과 집계

실제 검증 결과의 기본 단위는 Requirement가 아니라 Scenario다.

예:

```text
REQ-POST-002

필수 Scenario 2개

PASS        1
UNVERIFIED  1
```

이 경우 Requirement 전체를 PASS로 표시하지 않는다.

Requirement에는 다음처럼 Coverage를 표시한다.

```text
Verification Coverage
1 / 2
```

모든 필수 Scenario가 실제로 실행되고 PASS한 경우에만 해당 Requirement를 완전히 검증된 것으로 볼 수 있다.

# 33. Version 변경 규칙

Backend 구현만 바뀐 경우:

```text
같은 Scenario Version으로 다시 검증
```

API Contract가 바뀐 경우:

```text
관련 Scenario 재검토

→ 새 Scenario Version
```

Business Requirement가 바뀐 경우:

```text
API Contract 영향 확인

Scenario 영향 확인

→ 필요한 Version 갱신
```

Scenario 자체의 누락이나 오류를 수정한 경우:

```text
Requirement가 같아도
새 Scenario Version 생성
```

핵심 원칙:

> **동일한 승인 Version의 검증 기준은 다시 AI가 해석하지 않는다.**

# 57. 일반 AI Test Generator와의 차이

```text

↓

AI

↓

Code에 맞는 Test
```

현재 코드가 잘못되어 있으면 AI가 잘못된 구현을 정상 동작으로 받아들일 위험이 있다.

```text
Figma

↓

AI Requirement Extraction

↓

Human Clarification

↓

Approved Requirement

↓

Approved API Contract

↓

Approved Structured Scenario

     의미와 Expected 고정
──────────────────────────

↓

Backend Code

↓

Test Adapter

↓

Verification
```

즉 테스트의 정답과 검증할 상황이 모두 **Backend Code 바깥에서 먼저 결정된다.**
